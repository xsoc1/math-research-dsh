# Boundary and Non-Overlap Checklist

Run this checklist before dispatching a solver task and before closing a project stage.

## Request classification

- [ ] The request was classified as `PROGRAM_ONLY`, `PROGRAM_AND_DELEGATE`, or `SINGLE_PROBLEM_REDIRECT`.
- [ ] A single concrete proof/disproof/formalization/audit request was not retained in the manager workflow.
- [ ] Mixed requests separate project packaging from concrete mathematical work.

## No duplicated solver artifacts

- [ ] The manager did not create or replace `problem_contract.md`.
- [ ] The manager did not create or replace `repro_manifest.md`.
- [ ] The manager did not create or replace `status_and_literature.md`.
- [ ] The manager did not create or replace `obligation_graph.md`.
- [ ] The manager did not create or replace `approach_registry.md`.
- [ ] The manager did not create or replace `research_ledger.md`.
- [ ] The manager did not create or replace `counterexample_log.md`.
- [ ] The manager did not create or replace `candidate_proof.md`.
- [ ] The manager did not create or replace `audit_report.md`.
- [ ] The manager did not reproduce the upstream `reproducibility/` tree.
- [ ] Upstream artifacts are referenced by path/hash rather than copied into manager-authored equivalents.

## No duplicated mathematical workflow

- [ ] No theorem-contract or contract-audit procedure was implemented.
- [ ] No proof-obligation graph was built.
- [ ] No proof route portfolio or dynamic route search was run.
- [ ] No concrete proof, counterexample, or construction was generated by the manager.
- [ ] No problem-level computation-to-proof bridge was designed by the manager.
- [ ] No proof-agent role system or scheduler was introduced.
- [ ] No candidate proof was synthesized, adversarially audited, or revised by the manager.
- [ ] No formal-proof workflow was implemented.
- [ ] No individual-result correctness, completeness, or novelty audit was performed.
- [ ] No replacement result labels or reporting protocol were defined.

## Correct delegation

- [ ] The call names `$rigorous-open-math-research` rather than an absolute filesystem path.
- [ ] The task packet is clearly labeled project context, not a verified theorem contract.
- [ ] Original paper sources and exact versions accompany relevant notes.
- [ ] The upstream skill is instructed to recheck exact statements and hypotheses.
- [ ] The dependency direction remains manager to solver only.


## Accepted-knowledge boundaries

- [ ] The accepted-knowledge pipeline ran only when the user authorized acceptance.
- [ ] The acceptance review covered evidence completeness, classification, and hash binding only; it did not re-audit the mathematical proof.
- [ ] The reviewer agent ID differs from the author agent ID.
- [ ] Canonical `knowledge/blueprint.json` and `knowledge/evidence_inventory.csv` changed only through the deterministic receiver.
- [ ] Submission artifacts are immutable; corrections use a new submission with `supersedes`.
- [ ] Every reusable knowledge item carries one epistemic class; basic assumptions carry exact sources, stable identifiers, locators, and a consensus explanation.
- [ ] Task packets and research sub-agents were bound to a knowledge snapshot; a `SNAPSHOT_MISMATCH` invalidated accumulated retrieval.
- [ ] The latest accepted-knowledge snapshot hash is recorded in the checkpoint and `state/current.json`.

## Mathematics-knowledge boundaries

- [ ] Research-state records (goals, obligations, inference statuses, audited failures) are recorded as accepted statuses; the manager did not produce a proof, refutation, audit, or novelty judgment.
- [ ] Claims and inferences carry the specialized status, and only `proved` inferences are treated as truth-propagating.
- [ ] A proved inference binds a content-hashed proof package with `unresolved_obligations: []`; refutations bind packages; verified counterexamples bind certificates.
- [ ] Proof approval records passing definition, logic, boundary, and adversarial audits bound to the exact proof-package hash.
- [ ] Transaction status is kept separate from research status: `merged` is not `solved`; a merged partial lemma is `research_status: partial_progress`.
- [ ] The post-merge trusted closure (`math-closure`) and goal frontier (`math-frontier`) were recomputed and recorded.
## Correct ingestion

- [ ] The upstream status is stored verbatim.
- [ ] Proof and audit artifacts are linked independently when present.
- [ ] Missing artifacts or unknown fields are stated explicitly.
- [ ] Reusable tools are no broader than their source or audited result.
- [ ] Project portfolio states are not presented as mathematical result statuses.
- [ ] Stage summaries distinguish management completion from theorem completion.
