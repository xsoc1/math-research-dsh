# Stage C formalization protocol

Read this file completely before doing Stage C work. It expands the hard
Stage C boundary in `SKILL.md`; it does not weaken that boundary.

## Formalization decision

Every run records its formalization decision in `run-manifest.json`
(`formalization: requested | not_requested | skipped | scaffold`). A skipped
lean-verify step must be a recorded decision, never a silent omission.

- `requested` -- the formalizer/verifier agents MUST run, and the run must
  reference the produced `lean-proof/run-manifest.json` in
  `formalization_manifest`; `lean-proof/verification.json` must exist with a
  clean machine verdict.
- `scaffold` -- a Lean scaffold file was created for the new result(s); the
  run must reference it in `formalization_manifest` (a `.lean` file or
  `formalization_progress.md`). Scaffolds are not verified artifacts and must
  not be reported as `FORMALLY_VERIFIED`.
- `skipped` -- requires a non-placeholder `formalization_reason`, for example
  a tool outage, and the re-verification obligation must stay open in the
  obligation graph.
- `not_requested` -- the user did not ask for formalization for this result.
  This is allowed only for runs without material progress or before the
  scaffold cutover.

The stage gate enforces all four mechanically. A run claiming a completion
label without a decision fails. New runs started on or after 2026-08-16 with
material progress must record `scaffold` or `requested`.

## Verification workflow

1. Create or update the Lean project under `lean-proof/`, and map each
   obligation to a `.lean` declaration using an O1..On obligation map.
2. The formalizer writes the Lean files. The verifier runs
   `verify_lean_project.py --project . --build`, including the sorry/axiom scan
   and `lake build`, and refreshes `run-manifest.json`.
3. Write or extend `audit_report.md` for per-obligation fidelity and
   `verification.json` for the structured verdict. Update `STATUS.md` and
   `README.md`. Fix source-document errors in place and record them as F-xxx in
   the audit report; never silently change sources.
4. Require build exit 0, zero sorry/admit/axiom hits, and a complete obligation
   map. Without this machine evidence, do not report `FORMALLY_VERIFIED`.

## Partial results and verification tiers

When a run closes with a partial or structural result such as
`RIGOROUS_PARTIAL_RESULT`, the formalizer writes a Lean scaffold under
`lean-proof/`. It states the new declarations and open obligations, marks
unfinished blocks with `sorry` and a `-- SCAFFOLD` header, and updates
`lean-proof/STATUS.md`, `lean-proof/README.md`, and
`formalization_progress.md`. This is not full verification and must never be
labeled `FORMALLY_VERIFIED`.

Use the cheapest sufficient verification tier:

- Tier 0: statement scaffold with `sorry` and a compilable skeleton.
- Tier 1: machine-check a load-bearing lemma with `lean_verify`.
- Tier 2: full `lake build`, zero sorry/axiom hits, and independent audit. Only
  this tier may support `FORMALLY_VERIFIED`, and full verification is reserved
  for completion labels.

Intermediate verification is encouraged throughout Stage B and Stage C.
Verify load-bearing lemmas as soon as they are stable, not only at the end. A
machine-checked intermediate lemma is a valid checkpoint that reduces detours.

## Audit, reuse, and supersession

Every submission is checked on two tracks: the informal Danus-style
natural-language audit and the Lean formal track. Record both in the
verification matrix described by `references/dual-track-audit.md` in the
rigorous skill. Informal gaps trump a passing Lean check, Lean failures trump a
passing informal check, and paper-level failures trump both.

Before proving a new lemma, check `lean-proof/LEMMA_INDEX.md`, generated by
`scripts/index_lean_lemmas.py` in the manage skill. If the declaration already
exists, import or reuse it instead of re-proving it, and record the reuse in
the run ledger.

When a newer, more advanced result covers an older scaffold, partial result, or
formalized result, mark the older entry `superseded` in
`lean-proof/STATUS.md`, `README.md`, and `formalization_progress.md`, with a
pointer to the superseding result. Keep the old files and history. Never
present a superseded result as the current state.

## Lean escalation and repair

When a proof-critical claim is load-bearing and machine verification is
available, formalize that claim before claiming the completion status, rather
than as a post-hoc audit. Escalate the lemma into the Lean project, verify it,
and only then claim the label. This prioritizes key claims and does not replace
the final stage gate. This rule was distilled from dsh-rigorquant:
https://github.com/linxichen/dsh-rigorquant.

Formalization errors are feedback, not dead ends. On every Lean failure,
classify the error as statement, proof, dependency, or boundary-convention,
then repair at the correct layer:

- If the flaw is in the Lean proof, repair the Lean file and re-verify. The
  statement is frozen: a statement change starts a new audit, not a repair.
- If the flaw is in the natural-language proof, route it back to the solve-run
  lead, fix the candidate proof, re-audit the affected obligations, and then
  re-formalize. Never patch the formalization around a real source-argument
  flaw.
- Keep bounded loops, 5-15 rounds per file by default. Then report the exact
  obstacle instead of weakening the claim.
